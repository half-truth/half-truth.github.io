UJM｜用 gh 管理 SSH Key：从入口到出口

在干嘛：P0 是整条旅程的地基——身份与凭据。没有它，后面 P1～P10 的每一条命令都会被 401/403 拦住。这一环节管理的是 SSH 密钥（以及同属身份范畴的 GPG 签名密钥、OAuth 授权）的生成、登记、验证与退役。特征：低频、高风险、全局影响——一次配置长期生效，配错或误删影响所有仓库。
入口/出口 环境检查 生成与登记 验证 轮换与退役
入口

用户意图："我要让这台机器能安全地连上 GitHub"

典型触发：新装机器/新系统首次使用 gh；clone 时报 Permission denied (publickey)；换了电脑要把旧密钥带过来或重建；安全要求轮换密钥；组织要求 commit 签名。

检查

先看现状：登录状态与已有密钥

$ gh auth status # 是否已登录、scope 是否健康 $ gh ssh-key list # 账号下已登记的 SSH 公钥 $ gh gpg-key list # 已登记的 GPG 签名密钥
注意：① gh ssh-key list 列的是"已上传到 GitHub 的公钥"，本地 ~/.ssh 里的私钥它管不到；② auth status 显示的 token scope 决定了后面哪些命令能用，缺 scope 用 gh auth refresh -s … 补。

┈┈┈ 三条支线 ┈┈┈

支线 ①

生成与登记

$ ssh-keygen -t ed25519 -C "you@example.com" $ gh ssh-key add ~/.ssh/id_ed25519.pub \ --title "workbook-2026" # 顺手完成 gh 登录（浏览器 OAuth 流程） $ gh auth login
注意：① 算法选 ed25519（短、快、安全），别再用 RSA 旧参数；② 公钥要带 --title 标明设备，否则日后轮换时分不清哪把钥匙是哪台机器；③ 私钥永不离开本机——要上传的只有 .pub；④ passphrase 强烈建议设置，配合 ssh-agent 免重复输入。
支线 ②

验证连通

$ ssh -T git@github.com # Hi yourname! You've successfully authenticated. $ gh repo clone owner/repo # 真实场景试一把
注意：① ssh -T git@github.com 是标准自检，报 Permission denied 时先确认 ssh-add -l 里 agent 有没有加载私钥；② clone 走 SSH 协议要求仓库地址是 git@github.com:… 形态，HTTPS 形态走的是 token 而非 SSH key——分清两种通道。
支线 ③

轮换与退役

$ gh ssh-key list # 找到要退役的 key ID $ gh ssh-key delete <key-id> # 从 GitHub 移除公钥 $ gh gpg-key delete <key-id> # GPG 同理
注意：① 换机器的正确姿势是先 add 新 key、验证通过、再 delete 旧 key，避免真空期；② delete 是全旅程安全敏感度最高的删除操作——删错当前在用的 key 会导致所有仓库立即失联（P10 已明确把凭据删除划归本环节，不在 P10 做）；③ 离职/退役设备：删除公钥 + 本机销毁私钥。
出口

目标达成：身份通道就绪，P1～P10 全部畅通

验证 ssh -T 通过、gh auth status 健康。P0 之后的所有环节都默认这个前提成立——任何时候 P1～P10 突然出现 403/Permission denied，先回 P0 排查，这是旅程的"回炉入口"。

低频、高风险、全局影响凭据类删除动作全部归此，不归 P10
易踩坑速记：① ed25519 优先　② 公钥加 --title 标设备　③ ssh -T 自检后再干活　④ 换机先加新后删旧　⑤ delete key 前 triple-check——删错即全站失联。

UJM｜P1 工具环境个性化：让 gh 顺手起来

在干嘛：P1 调教的是gh 工具本身——默认编辑器、命令别名、扩展插件。它同样低频、且作用于"每一次后续操作"：P4 的 gh gist edit、P5 的 review 描述、P8 的 copilot 扩展，全都依赖 P1 的配置质量。P1 与 P0 并列为基础层：P0 解决"能不能用"，P1 解决"顺不顺手"。
入口/出口 编辑器 别名 扩展
入口

用户意图："gh 能用了，但用起来别扭"

典型触发：gh 命令弹出的编辑器是 nano 想换 vim/vscode；常用命令太长想造别名；想要 copilot、metrics 这类官方没有的子命令。

┈┈┈ 三条支线 ┈┈┈

支线 ①

编辑器配置

$ gh config set editor "code --wait" $ gh config set editor "vim" # 按口味选 $ gh config list # 查看当前配置
注意：① --wait（或等效阻塞参数）不可少——VSCode 默认立即返回，gh 会以为你写完了，导致内容为空；② 受影响的命令：gist edit、issue/pr create 的 body、pr review 等，凡是"弹出编辑器"的场景都吃这个配置。
支线 ②

别名

$ gh alias set co "pr checkout" $ gh alias set myissues "issue list --assignee @me --state open" $ gh alias list $ gh alias delete co # 删除别名归 P1，不归 P10
注意：① 别名是把支撑层的高频组合（如 --json --jq 查询）固化的唯一正确归宿——P7 判读逻辑定型后就来这里造别名；② 命名用短助记（co / ci / myissues），造完实际跑一遍验证；③ 别名存于 gh 配置文件，跟机器走，换机器要重建。
支线 ③

扩展

$ gh extension search copilot $ gh extension install github/gh-copilot $ gh extension list $ gh extension remove github/gh-copilot # 移除归 P1
注意：① 扩展本质是 git 仓库里的可执行脚本，gh ext upgrade --all 定期升级；② extension remove / alias delete 均属"工具配置"操作，归 P1 不归 P10（P10 只管工作产物）——这是本次边界修正的重要一环；③ 安装第三方扩展前看一眼源码，扩展以你的 token 权限运行。
出口

目标达成：工具链顺手，后续环节零摩擦

判据很简单：接下来一周里，每当你想在 P3～P10 干什么，不再因为工具别扭而停顿。P1 可随时重入（新别名、新扩展都是新入口），配置的长期清理也在这里而不是 P10。

P0 管能不能用，P1 管顺不顺手extension/alias 的增删都归 P1
易踩坑速记：① code 编辑器必须带 --wait　② 高频组合查询固化为 alias　③ 扩展以你的 token 权限运行，装前看源码　④ 换机器别名/编辑器配置要重建。

UJM｜P2 发现与定位：在海量资源里找到目标

在干嘛：P2 的对象是未知的资源——不知道仓库在哪、不知道某功能有没有现成实现、不知道某个报错的出处。它与 P7 的分界与 P9 同理：P7 查已知资源的状态，P2 找未知资源的位置。出口判据：拿到一个明确的"目标坐标"（仓库 URL / issue 编号 / 文件路径），移交 P3～P6 处理。
入口/出口 全局搜索 查看定位
入口

用户意图："这个东西在哪 / 有没有现成的"

典型触发：找某语言的轮子；查某报错是否已有 issue；调研组织里有哪些同类服务；接手陌生项目想先看看全貌。

┈┈┈ 搜索 → 查看 → 定位 ┈┈┈

动作 ①

全局搜索

$ gh search repos "cli tool" --language go --sort stars --limit 10 $ gh search issues "ECONNREFUSED" --repo owner/repo --state open $ gh search code "TODO: refactor" --owner my-org $ gh search prs --author @me --state merged
注意：① search 系列都支持 --json --jq（支撑层④），结果可直接编程；② code 搜索需要登录且只搜默认分支；③ 搜到自己收藏里用 --starred --owner @me（P6 star 的召回入口就在这）。
动作 ②

查看与确认

$ gh repo view owner/repo # README 全貌 $ gh issue view <n> -R owner/repo --comments $ gh repo view owner/repo --web # 跳网页细看（支撑层②）
注意：① view 是"确认这是不是你要的目标"，别在这一步做接入动作；② 复杂的图形化比较（分支图、依赖图）跳 --web。
出口

目标达成：拿到明确坐标，移交下游

仓库 → P3 接入；issue/PR → P5 参与；灵感/缺口 → P4 创造；候选目标多起来 → P6 收藏归档。P2 每次产出都是"坐标"，不产生任何资源变更。

P2 找未知的，P7 查已知的产出 = 坐标，无副作用
易踩坑速记：① search 结果配 --json --jq 可编程　② code search 只搜默认分支　③ 确认目标用 view，别混入接入动作。

UJM｜P3 获取与接入：把"远方的资源"变成"手边的工作台"

在干嘛：前提是对象已知（来自 P2 或别人给的链接）。选择一个接入方式，让它变成可直接操作的东西。出口判据：动作结束后，你手里出现了一个能立刻开始工作的入口。核心决策是接入方式四选一。
入口/出口 方式决策 本地接入 云端接入 产物下载 内容读取
入口

用户意图："目标确定了，我要开始干活"

典型触发：P2 搜到了目标仓库；同事说"看下这个 PR"；要装某个项目的发布包；CI 挂了要拿产物排查；别人分享了一个 Gist 链接。

决策

接入方式四选一（关键问题：你要"做什么"）

① 本地读写代码、跑构建、改代码 → 本地接入（clone / fork / pr checkout） ② 代码重、本机环境装不了、要算力 → 云端接入（codespace） ③ 只要成品不要源码（安装包/构建产物）→ 产物下载（release / run download） ④ 只想看一段文本/配置/脚本 → 内容读取（gist view --raw）
注意：本地 vs 云端是本环节最大的分水岭——本地快但受限于本机环境，云端重但环境开箱即用。repo 大（>1GB）、依赖奇怪、需要 Linux 环境时优先考虑云端。

┈┈┈ 按接入方式选择分支 ┈┈┈

分支 ①

本地接入

$ gh repo clone owner/repo $ gh repo fork owner/repo --clone # 贡献他人项目 $ gh pr checkout <number> # 本地验证他人 PR（需已在仓库目录内）
注意：① clone 报 publickey 错误 → 回 P0，SSH 通道没通；② fork --clone 会建立 your-fork/上游 的标准结构，push 推到 fork、PR 对上游；③ pr checkout 后本地处于他人分支，验证完记得 checkout 回自己的分支。
分支 ②

云端接入（Codespaces）

$ gh cs create -R owner/repo $ gh cs list # 看有哪些环境（也归 P7/P10 巡检） $ gh cs ssh -c <name> # 终端进入 $ gh cs stop -c <name> # 用完先停（省钱，详见 P10）
注意：① Codespaces 是唯一持续计费的接入方式（机器 × 挂机时长）——用完即 stop 的习惯从 P3 就要建立；② cs create 首次启动要几分钟，别误以为卡死；③ 环境里未 push 的代码只存在于云端，删除环境前先推回远端。
分支 ③

产物下载

$ gh release download v1.2.0 -R owner/repo --pattern '*.tar.gz' $ gh run download <run-id> -n build-artifacts # CI 产物 $ gh attestation verify ./app.tar.gz -R owner/repo # 来源校验（衔接 P9）
注意：① 下载的二进制先验证来源再运行（P9 的 attestation verify），这是供应链安全的基本动作；② run download 需要 workflow 声明了 upload-artifact，否则列表为空；③ release 产物与源码包（Source code zip）是两回事，按 pattern 精确取。
分支 ④

内容读取

$ gh gist view <id> --raw > script.sh $ gh gist view <id> --files # 多文件 gist 先看清单
注意：① --raw 重定向拿到纯文本，可直接执行前先读内容再跑别人的脚本；② gist 无版本依赖关系，取完即用，来源更新需自行 re-fetch。
出口

目标达成：工作入口就绪

本地目录 / 云端环境 / 下载产物 / 文本文件——四者任一就绪即出口。去向：改代码 → P4；参与讨论 → P5；产物部署运行前 → P9 验证；闲置接入物（停掉的 cs、过时产物）→ 日后 P10。

出口判据唯一：能立刻开始工作云端接入引入计费，用完即停
易踩坑速记：① publickey 报错回 P0　② cs 用完 stop，别挂着计费　③ 二进制先 attestation verify 再跑　④ pr checkout 完记得切回自己分支。

UJM｜P4 内容创造与完善：从无到有，单边打磨

在干嘛：全旅程中唯一"从无到有"制造资源的环节——建仓库、发版本、写 Gist、搭看板、提 issue/PR。核心特征是单边维护：不需要等任何人回应就能持续推进。通用节奏是"创建 → 打磨 → 达到可用形态"的循环，五类资源共享同一骨架。关键切分：issue/PR 的 create 归 P4，提出后的流转归 P5。
入口/出口 对象决策 仓库 发布/工作项 Gist/看板
入口

用户意图："我要产出点东西"

典型触发：有了新项目想法要开仓库；代码写完要发版；攒了个好用的脚本想分享；项目要立项建看板；发现 bug / 写完功能要提 issue 或 PR。

决策

要产出的是什么类型的资源？

① 一个新项目的家（容器） → 仓库 repo create ② 一版正式成品 → 发布 release create ③ 一段值得分享的文本/脚本 → 代码片段 gist create ④ 规划框架（组织级） → 看板 project create ⑤ 一个问题或一次贡献 → 工作项 issue/ pr create
注意：五类资源有依赖关系——release/gist/issue/PR 挂在仓库下，看板可收 issue。首次做新项目顺序 ①→（④⑤ 可选）→②；在已有仓库里工作直接从 ②③⑤ 进入。

┈┈┈ 按资源类型选择分支（每条 = 创建→打磨循环）┈┈┈

分支 ①

仓库｜创建容器

$ gh repo create my-project \ --public --clone --add-readme $ gh repo create my-project --private # 先私有后公开 $ gh repo create org-name/my-project --public
注意：① --clone 建完直接拉到本地，省一步 P3；② --add-readme 让仓库立即有初始提交；③ 可见性随时可改；④ 组织仓库需要权限，403 是权限问题。
分支 ②

发布｜产出 + 迭代完善

$ gh release create v1.0.0 --generate-notes ./dist/app.tar.gz $ gh release upload v1.0.0 ./dist/app.zip --clobber $ gh release edit v1.0.0 --notes "修正后的说明"
注意：① --generate-notes 自动汇总变更；② upload 覆盖要 --clobber；③ tag 已存在时 create 失败，先 list 看冲突；④ 大量下载后别改产物，发新 tag。
分支 ③

Gist｜产出 + 修订

$ gh gist create deploy.sh --desc "一键部署脚本" --public $ gh gist edit <id> $ gh gist rename <id> --filename "v2-deploy.sh"
注意：① edit 调用 P1 配好的 editor；② secret Gist ≠ 私密——拿到 URL 就能看，别放密钥；③ gist 有版本历史。
分支 ④

看板｜建立规划框架

$ gh project create --owner my-org --title "2026 Q4 路线图" $ gh project edit <number> --owner my-org --title "…v2"
注意：① 组织级看板需要 scope，gh auth refresh -s project 补授权（回 P0）；② 看板 CLI 能力官方子命令中最弱，字段值更新用 gh api graphql（支撑层兜底）；③ issue 纳入看板是 item-add，归 P6。
分支 ⑤

工作项｜首次提出

$ gh issue create --title "登录页在 Safari 下白屏" \ --body "复现步骤：…" --label bug $ gh pr create --fill # 用首个 commit 信息自动填
注意：① pr create 前提是分支已 push，报 no commits 就是忘了 push 或基分支错；② --fill 只做初稿；③ 到此为止是 P4 终点——提出后的评论/审阅/合并是 P5。
汇合验证

达到"可用形态"了吗？

仓库： gh repo view my-project --web 自查：他人能否仅凭 URL 理解项目？ 发布： gh release view v1.0.0　产物齐全、说明完整？ Gist： gh gist view <id> --web　内容自解释？ 看板： gh project view <n> --owner my-org --web　结构满足规划？ 工作项： gh issue view <n>　标题能让人 3 秒看懂？
注意：统一判据——"交给一个毫不知情的人，他能否直接使用/继续？"达不到就回分支打磨。
出口

目标达成：资源达到可用形态

去向：issue/PR 提出 → P5；release/Gist → 交付他人（进入他们的 P3）；看板/仓库长期存活，清理归 P10。打磨循环随时重入——edit 命令都是重新进入 P4 的入口。

create 归 P4，流转归 P5edit 即重入入口
易踩坑速记：① repo create 记得 --clone --add-readme　② upload 覆盖要 --clobber　③ secret gist 不私密　④ pr create 报 no commits = 忘 push　⑤ issue/PR 的 create 与流转的分界线 = P4 与 P5 的分界线。

UJM｜P5 协作推进：在别人的回合之间走棋

在干嘛：P5 处理已存在、状态机不由你一个人掌控的工作项（issue/PR）。节奏与 P4 截然不同：你走一步 → 球在别人那边 → 等待 → 看别人做了什么 → 决定下一步。因此 P5 的 UJM 是"检查状态 → 依状态行动 → 等待 → 再检查"的循环，而非直线。
入口/出口 状态检查 回应/元数据 审阅/合并 终点
入口

用户意图："有个工作项在等我，或该我出手了"

$ gh status # 全局聚合：分配给我的 / 提及我的 / 我 review 的 $ gh pr list --assignee @me $ gh issue list --assignee @me
循环起点

检查状态：球现在在谁那边？

$ gh pr view <n> --comments $ gh pr checks <n> $ gh pr view <n> --json state,reviewDecision \ --jq '"\(.state) | review: \(.reviewDecision)"' $ gh issue view <n> --comments
注意：① P5 第一动作永远是"看"；② 关键字段 state 与 reviewDecision——后者决定你该改代码还是该催合并；③ issue 主要看最后一条评论方向和 label。

┈┈┈ 依状态选择你的"这一手" ┈┈┈

状态 A

回应讨论 / 补充信息

$ gh issue comment <n> --body "已确认，是 Safari 特有的 CSP 问题" $ gh pr comment <n> --body "这版已修复，请再看" $ git push origin my-branch # 改完 push，PR 自动更新
注意：① 评论是永久公开记录；② 回应 review 的惯例是改完代码 + 评论指出改了什么；③ 长内容用 --body-file note.md 免 shell 转义。
状态 B

调整元数据 / 调度资源

$ gh pr edit <n> --add-reviewer alice,bob $ gh issue edit <n> --add-label "priority:high" $ gh issue edit <n> --add-assignee @me $ gh issue edit <n> --milestone "v2.0"
注意：① 打 label 需 triage 及以上权限；② label 是协作的"调度语言"，遵循仓库既有体系（衔接 P6）；③ 指派 reviewer 后你会出现在对方 gh status 里，别乱点将。
状态 C

审阅表态

$ gh pr checkout <n> # 先本地看真实效果 $ npm test $ gh pr review <n> --approve $ gh pr review <n> --request-changes --body "第 42 行有越界风险" $ gh pr review <n> --comment --body "先问个问题"
注意：① request-changes 有阻断力，小问题用 comment；② approve 自己的 PR 无效；③ 批准前先跑测试——批准了没验证的代码你也在责任链上。
状态 D

合并落地（通常不可逆）

$ gh pr checks <n> # 三条全绿才动手 $ gh pr merge <n> --squash --delete-branch $ gh pr merge <n> --auto # 条件没齐？挂自动合并
注意：① 合并方式由仓库统一约定；② --squash + --delete-branch 最常用，本地分支自己删；③ --auto 代替干等，最易忽略的省心功能；④ merge 后历史封存，revert 是新增反向提交不是撤销。
状态 E

终点：关闭（仍可逆）

$ gh issue close <n> --comment "已修复于 #45" $ gh pr close <n> $ gh issue reopen <n> / gh pr reopen <n>
注意：① 关 issue 留关联引用（fixed by #45）；② issue 由提出者或维护者关，别随手关别人的；③ PR close 后想复活需分支还在。
等待与循环

出手之后：球在别人那边——离开，下次再回来

A～C 每个动作后都回到等待状态。不要原地轮询刷新——让通知和 gh status 在下次会话告诉你有什么变了。

⏳ 等待他人动作 → 下次从"循环起点"重新进入
注意："什么都不做"也是正确操作——频繁催促不推进状态机，用 --auto 和通知机制替你盯着。
出口

状态机走到 merged 或 closed

merged → 代码进主干，关联 issue 自动关闭；closed → 归档。都可 reopen。合并产生的下一个 release 回到 P4；长期清理归 P10。

循环体：检查→行动→等待→再检查merge 不可逆，其余终点可逆
易踩坑速记：① 先 gh status 再动手　② request-changes 是阻断性表态　③ --auto 挂机等 CI　④ squash 后本地分支自己删　⑤ 关 issue 留关联　⑥ 别人回合时"不动"也是一手。
产品视角：通知驱动的任务收件箱；操作的 UI 重量应与其可逆性成正比。

UJM｜P6 组织与分类：先建体系，再挂内容

在干嘛：资源多到看不过来时，建立分类体系——label 定义维度、Project 搭规划结构、star 做个人收藏。与 P5 的根本区别：P6 不改变任何协作状态，只做"归置"，服务未来的 P2（检索）和 P5（路由）。正确节奏：先定义体系、再批量挂内容。
入口/出口 体系盘点 Label Project Star
入口

用户意图："东西多了，找不到了"

典型触发：issue 积了几十条没优先级；新仓库默认 label 不够用；团队要按季度规划；想把优质仓库攒起来日后回访。

盘点

先看现状，再定体系（这步省不得）

$ gh label list --repo owner/repo $ gh project list --owner my-org $ gh project field-list <number> --owner my-org
注意：① label 被大量使用后再改名成本极高，盘点防返工；② 仓库多时优先 clone 现成体系而非自建。

┈┈┈ 三条独立支线 ┈┈┈

支线 A

Label 体系｜定义分类维度

$ gh label create "priority:high" --color "d73a4a" \ --description "两周内必须处理" $ gh label clone owner/template-repo --repo my-new-repo 命名惯例：priority:high / type:bug / area:api（维度前缀分组）
注意：① 先定命名规范再动手——"bug"与"type:bug"混用是体系腐烂的开始；② clone 是整套复制，先 list 再搬；③ label 描述务必写——它是协作者理解体系的唯一说明书。
支线 B

Project 规划｜搭结构、挂内容

$ gh project create --owner my-org --title "Q4 路线图" $ gh project field-create <n> --owner my-org \ --data-type SINGLE_SELECT --name 状态 \ --single-select-options "未开始,进行中,已完成" $ gh project item-add <n> --owner my-org \ --url https://github.com/owner/repo/issues/123 $ gh project field-list <n> --owner my-org
注意：① item-add 用完整 URL 不是编号；② 字段值更新 CLI 做不了，用 gh api graphql 兜底；③ Project 是组织/用户级资源，权限跟 owner 走。
支线 C

Star 收藏｜个人化标记

$ gh repo star owner/repo / gh repo unstar owner/repo $ gh search repos --starred --owner @me --language rust # 收藏要能召回
注意：① star 是纯个人行为，不影响仓库状态；② star ≠ watch：star 是收藏，watch 是收通知（gh status 里那堆 Repository Activity 动态的来源就是 watch，别搞混）；③ 收藏多了靠 search 召回，别翻页。
汇合验证

用体系跑通一次真实的检索/规划

Label： gh issue list --label "priority:high" → 筛得出结果？ Project： gh project item-list <n> --owner my-org → 挂上了？可分组？ Star： gh search repos --starred --owner @me → 关键词能召回？
注意：最大陷阱是过度设计——从 3~5 个 label 和一个字段开始，体系是长出来的，空转的 label 会变成噪音。
出口

分类骨架可用，资源已归位

之后转入后台维护态：日常由 P4/P5 的工作项自动流入，P2 检索按维度召回。重入触发：体系迭代、积压重整；失效体系清理归 P10。

不改变任何协作状态服务 P2 检索 / P5 路由
易踩坑速记：① label 命名先定规范　② clone 先 list 再搬　③ item-add 要完整 URL　④ Project 字段值用 gh api graphql　⑤ star ≠ watch　⑥ 从最小可用开始。

UJM｜P7 状态感知：只看不动，看完决定去哪

在干嘛：每次打开终端的固定起点——全局扫一眼"世界发生了什么变化"，再决定这次会话去哪个 Purpose。三个硬性特征：只读、面向已知资源（非 P2 的大海捞针）、输出是决策依据（看完必须产生"下一步去哪"的结论，否则就是刷屏式无效感知）。
入口/出口 全局扫描/判读 工作项/CI 环境/发布/缓存
入口

会话起点："我回来了，世界有什么变化？"

不带具体任务来，先看全局——让状态决定今天做什么。

触发频率：全旅程最高频P5 的"等待"在此被唤醒
第一层

全局聚合扫描

$ gh status # 全景：Assigned / Review / Mentions / Repo Activity $ gh status -o my-org # 收窄到某组织 $ gh org list # 确认归属（冷启动时） $ gh auth status
注意：① 四区块各有含义——Assigned 是"欠别人的"，Review Requests 是"别人求你的"，Mentions 是"有人叫你"，Repository Activity 是 watch 的仓库动态，不是你参与的；② gh status 为空 ≠ 没事干，例行巡检（CI/缓存/环境）要主动查。

┈┈┈ 第二层：定向深查 ┈┈┈

深查 A

工作项与 CI 进展

$ gh issue list --assignee @me $ gh pr list --author @me --state open $ gh run view <id> --watch # 阻塞式盯到结束 $ gh pr checks <n> $ gh run list --limit 5 --branch main $ gh run view <id> --log-failed
注意：① --watch 阻塞终端，CI 长时用定时回查；② checks 红 → P4 修，绿+review 过 → P5 合；③ run list 加 --branch 收窄噪音。
深查 B

环境 / 发布 / 缓存

$ gh cs list / gh cs view -c <name> $ gh release list --repo owner/repo $ gh release view v1.2.0 $ gh cache list --repo owner/repo --sort size_at_created
注意：① Stopped/闲置环境就是 P10 的活——记下来稍后清理；② cache 有总容量配额，占满拖慢 CI，异常就去 P10（gh cache delete）；③ release view 常用于发版前对照上一版（P4 的输入）。
判读

把观察翻译成路由决策（P7 的真正产出）

有要我 review 的 / PR 被要求改 → P5 协作推进 CI 红了 / 要修 bug 写功能 → P4 修改代码、提交 要拉仓库 / 装产物 → P3 获取与接入 工作项积压、label 混乱 → P6 组织与分类 闲置环境 / 缓存超配额 → P10 清理收尾 一切正常 → 今天没有我的活，正常离开 ✓
注意：最大反模式是"只刷不决"——每个查询都应以"所以我接下来去……"收尾；连续两次没结论就该离开终端。
出口

决策依据到手，路由到对应 Purpose

P7 不产出资源、不改状态，是所有其他 Purpose 的调度器。日常心跳：感知 → 行动 → 等待 → 再感知。

全程只读、零风险出口 = 一条路由决策，而非一屏查询结果
易踩坑速记：① Repository Activity 是 watch 动态不是参与记录　② --watch 阻塞终端　③ Stopped 环境记下来去 P10　④ cache 占满拖慢 CI　⑤ 每次查询以"所以我去……"收尾。
产品视角：P7 必须是默认首页，每张卡片内嵌下一步动作按钮，把"感知→路由"压到一次点击。

UJM｜P8 自动化配置与执行：今天定规矩，机器替你干活

在干嘛：P8 的独特之处在于受益者是未来——此刻每个动作都是为了"某次自动触发的流程"能正确运转：备凭据、点火验证、开关规则、失败重跑。与 P7 分工：P7 管"看"，P8 管"配置与点火"。安全敏感度最高的环节之一（secret）。
入口/出口 前置/验证 凭据 触发/开关 重跑
入口

用户意图："这件事不该我每次手动做"

典型触发：部署想自动化；CI 需要密钥但不想写进代码；某 workflow 半夜老挂想先禁用；deploy 失败只需重跑失败 job。

前置

盘点自动化资产现状

$ gh workflow list $ gh secret list # 只见名字不见值——正常的安全设计 $ gh variable list
注意：① secret 值一旦设置无法读取；② workflow yml 文件的增改走 git 提交流程（P4），P8 只管"运行层面"。

┈┈┈ 四个动作 ┈┈┈

动作 ①

凭据准备

$ gh secret set AWS_KEY # 交互式，值不进 shell 历史 $ gh secret set AWS_KEY < key.txt $ gh secret set AWS_KEY --env production # 环境级（可配审批） $ gh variable set DEPLOY_REGION --body "ap-east-1"
注意：① secret ≠ variable 的分界线是"泄露了会出事吗"；② 生产凭据强烈推荐 --env 环境级+审批保护，fork 的 PR 拿不到；③ echo "值" | gh secret set 会留 shell history，用交互式或文件重定向。
动作 ②

手动触发验证

$ gh workflow run deploy.yml -f environment=production -f version=v1.2.0 $ gh run list --workflow=deploy.yml --limit 1 $ gh run view <run-id> --log-failed
注意：① workflow 必须声明 workflow_dispatch 触发器；② run 是异步的——触发成功 ≠ 执行成功，必须接 run list/view 确认；③ 生产首触发先对 staging 验证。
动作 ③

规则开关管控

$ gh workflow disable deploy.yml # 止血：密钥待换/误触发 $ gh workflow enable deploy.yml
注意：① disable 是全局开关（手动/定时/push 全失效）；② 禁用超 60 天的定时 workflow 会被 GitHub 自动停用；③ 谁关的最好留 issue 记录。
动作 ④

失败重跑

$ gh run rerun <id> --failed # 只重跑失败的 job ✓ 偶发失败（网络抖动/flaky）→ rerun 合理 ✗ 必然失败（bug/配置错） → rerun 无效，先去 P4 修
注意：① rerun 用当时的代码快照——期间改过的不会生效，改完应重新触发；② 连续失败三次请认真看日志，反复 rerun 是浪费。
汇合验证

自动化处于受控状态了吗？

凭据：gh secret list → 在列且更新时间符合预期？ 运行：gh run list → 最新触发成功完成？ 开关：gh workflow list → 该开的开、该关的关？
注意：P8 的事故特征是"静默失败"——不在场时挂掉没人知道，验证后确认通知渠道能触达你是最后一块拼图。
出口

机器接管，未来自动触发无需到场

日常监控交 P7；workflow 文件修改走 P4；废弃清理归 P10。回访触发：凭据轮换、失败告警、季度巡检。

受益者是未来而非当下secret 只写不读，安全敏感度最高
易踩坑速记：① secret 忘了只能重设　② 生产凭据用 --env+审批　③ workflow_dispatch 不声明触发不了　④ 触发≠成功　⑤ rerun 用旧快照　⑥ disable 60 天自动停用　⑦ 通知渠道必须验证。
产品视角：自动化控制台视图，secret 区域只写不读，rerun 按钮预选失败 job。

UJM｜P9 验证与治理：它可信吗？它合规吗？

在干嘛：回答两个与"进展"无关的问题——真实性（产物真来自它声称的构建流程吗）与合规性（符合组织规则吗）。与 P7 分界：P7 看时间轴（跑到哪了），P9 看资格（够不够格）。唯一"结论只有通过/不通过"的环节——它不推动流程，但结论决定别的流程有没有资格继续。
入口/出口 疑问分流 产物溯源 规则巡检 不通过处置
入口

用户意图："我凭什么信它？"

典型触发：生产前确认二进制来源；接手团队仓库确认分支保护到位；安全审计要求证明产物未篡改。

分流

你的疑问属于哪一类？（操作者视角不同）

① 文件真是这个仓库构建的？→ 产物溯源（任何使用者） ② 分支能按规则合并/推送？→ 规则符合性（贡献者） ③ 组织规则配置健全吗？ → 治理巡检（管理者）

┈┈┈ 三条支线，结论都是二元判定 ┈┈┈

支线 ①

产物溯源（供应链安全）

$ gh attestation verify ./app.tar.gz -R owner/repo $ gh attestation verify ./app.tar.gz -R owner/repo \ --signer-workflow owner/repo/.github/workflows/release.yml # 推荐顺序：release download → attestation verify → 执行
注意：① 报 no attestations found 是产物没带证，不是你操作错；② 加 --signer-workflow 才是严格验证；③ 这是 P3"下载二进制先校验"的落地动作。
支线 ②

分支规则符合性检查

$ gh ruleset check --branch feature/my-work 缺 required checks → 回 P7 看 CI、P4 修 缺 required review → 回 P5 找人 approve
注意：① check 是只读预检，把"会被拒"提前到 push/merge 之前；② P9 只诊断，开药在别处；③ ruleset 与旧式 branch protection 并存时 check 会汇总两者。
支线 ③

组织级治理巡检

$ gh ruleset list --org my-org 巡检清单：关键仓库是否被 ruleset 覆盖？ 管理员豁免是否滥用？required checks 是否指向活着的 CI？
注意：① 需组织管理员权限；② 规则创建走网页端或 gh api（REST rulesets 端点），巡检（读）与修规（写）分开；③ 周期性动作，发现问题建 issue 跟踪（P4）。
关键分支

不通过怎么办？（只诊断，处置移交）

attestation 失败/无证 → 别运行！查下载渠道或向上游质询（P4/P5） check 缺 CI → P7 查 run、P4 修代码 check 缺 review → P5 请求审阅 巡检发现规则空洞 → 建 issue 提案（P4）
⚠ P9 最大的纪律："不通过就不继续"——没过的二进制再像正常也别跑；不过的合并别硬豁免。破坏这层纪律它就形同虚设。
出口

拿到明确的二元结论

通过 → 带信任凭证继续（产物运行、分支合并、巡检归档）；不通过 → 按分支处置移交。周期巡检构成治理心跳。

结论只有通过/不通过只诊断不开药
易踩坑速记：① no attestations found 是产物没证　② 严格验证加 --signer-workflow　③ check 缺什么去哪修　④ ruleset list 需管理员　⑤ 不通过就停手。
产品视角：门卫型功能——做成关键动作旁的轻量检查点（绿标/红横幅），常驻但不打扰，与 P7 的"默认首页"正相反。

UJM｜P10 工作产物维护与终结：收尾，省钱，减负 ✏️

在干嘛：让 P2～P9 产出的资源停止活跃或彻底消失，回收三类成本：真金白银（Codespaces 计费）、存储配额（cache/release）、注意力（无关通知）。核心心智是一根标尺：可逆的"停"优先，不可逆的"删"最后。
✅ 归 P10：P2～P9 链路产出的工作资源仓库、release、gist、run 记录、Codespace、cache、star——核心任务链路中诞生的东西。
❌ 不归 P10：身份与本地工具（本次修正的核心边界）ssh-key / gpg-key delete → P0；extension remove / alias delete → P1。删除它们是身份/环境管理，不是收尾。
入口/出口 盘点/验证 软终结（可逆） 硬删除（不可逆） 轻量清理
入口

"有东西该结束了"或"账单怎么又超了"

被动触发：账单异常、cache 告警、P7 巡检发现闲置；主动触发：项目完结归档、试验结束、季度例行清理。

盘点

列资产清单，算清谁在花钱/占地方

$ gh cs list # 持续烧钱的大头，先查 $ gh cache list --repo owner/repo --sort size_at_created $ gh release list --repo owner/repo $ gh run list --repo owner/repo --limit 20 $ gh repo list my-org
注意：① 盘点输出应是"处置清单"（每项标"停/删/不动"）；② Codespaces 是唯一持续烧钱的项；③ 删前想清依赖方——release 可能被别人引用。

┈┈┈ 三类动作 ┈┈┈

动作 A

软终结（可恢复）

$ gh cs stop -c <name> # 最常用的省钱动作 $ gh run cancel <run-id> # 挂死的 CI 止血 $ gh repo archive owner/old-project # 退役但只读可查
注意：① cs stop 只停计费不停存储，长期不用才 delete；② archive 可逆（unarchive），是项目退役的默认正确姿势；③ cancel 只对进行中的 run 有效。
动作 B

硬删除（不可恢复）

$ gh cs delete -c <name> / gh cs delete --all $ gh run delete <run-id> $ gh release delete v0.9-beta --cleanup-tag $ gh gist delete <id> $ gh cache delete --all --repo owner/repo

UJM｜支撑层：不构成旅程的一段，却衬着每一段

在干嘛：支撑层不是旅程中的一个环节——没有独立生命周期，嵌在 P0～P10 任何位置随时被调用。触发模式高度一致："官方子命令到这儿就不够用了"。五个工具对应五种"破局"方向，用完立即回到原 Purpose 继续。唯一红线：gh api 写操作失去子命令层的参数校验和防呆，误操作成本更高。
万能接口 跳转网页 脱离目录绑定 输出可编程化 命令辅助
进入

触发信号："子命令到这儿不够用了"

· 没有子命令？ → gh api / graphql · CLI 看配置太费劲？ → gh browse · 不想 cd 才能操作仓库？ → -R / --repo · 表格输出没法写脚本？ → --json + --jq · 命令怎么写记不清？ → gh copilot

最常见组合是 -R + --json + --jq（跨仓库 + 可编程），以及 gh api 兜底一切。

┈┈┈ 五个工具，五个破局方向 ┈┈┈

工具 ①

gh api / gh api graphql

方向：能力兜底　最常切入：P6，其次 P9/P10
# 经典案例：P6 中更新 Project item 字段值（CLI 做不到） $ gh api graphql -f query=' mutation { updateProjectV2ItemFieldValue( input: {projectId: "…", itemId: "…", fieldId: "…", value: {text: "高"}}) { projectV2Item { id } } }' # REST 同样直接：P10 调整 watch 订阅 $ gh api -X PUT repos/owner/repo/subscription -f ignored=true
注意：① graphql 是瑞士军刀——Project 高级操作几乎全靠它；② 写操作前先用 query 查目标 ID（查改两步走）；③ 复杂查询先在网页端 GraphQL Explorer 调通；④ 缺 scope 用 gh auth refresh -s … 补（回 P0）。
工具 ②

gh browse

方向：跳转网页端　最常切入：P9，其次 P2/P4
$ gh browse / gh browse -R owner/repo / gh browse <sha> 典型：P9 看规则集图形化配置、P4 预览 README 渲染
注意：① browse 是"接力棒"不是"逃跑出口"——做完事要回来；② 与 view 类命令的 --web 后缀功能重叠，哪种顺手用哪种；③ 带着任务跳，别漂在浏览器里失焦。
工具 ③

-R <owner/repo>

方向：脱离目录绑定　切入：所有仓库级命令
$ gh pr list -R owner/repo $ for repo in $(gh repo list my-org --json name --jq '.[].name'); do gh issue list -R "my-org/$repo" --label bug --json number --jq 'length' done
注意：① 忘加 -R 是最高频报错；② 批量读随便跑，批量写极度克制——先对单个仓库 dry-run；③ -R 要写全名 owner/repo。
工具 ④

--json + --jq

方向：输出可编程化　最常切入：P7，其次 P6/P10
$ gh pr list --json number,title,reviewDecision \ --jq '.[] | select(.reviewDecision=="APPROVED") | "\(.number) \(.title)"' # ↑ P7 判读路由的自动化版本 $ gh cs list --json name,state --jq '.[] | select(.state!="Shutdown") | .name' # ↑ P10 清理清单的生成器
注意：① --jq 是 gh 内置的，无需本机装 jq，但语法一致值得学；② 先裸跑 --json 看可用字段名；③ 这是"感知→行动"自动化的枢纽，定型逻辑写成别名（P1）。
工具 ⑤

gh copilot

方向：命令辅助　切入：贯穿所有 Purpose
$ gh copilot suggest "查找组织里最近一周更新的python仓库" $ gh copilot suggest "解释这个命令" -t shell "gh api graphql -f query='…'" # suggest（生成）/ explain（解释）两种模式
注意：① 生成的命令先读再跑——AI 建议不背你的责任，尤其 api 写操作；② explain 模式是读懂别人脚本的最佳工具；③ 安装与授权归 P1。
进阶

组合拳：支撑层的真实使用形态

# 组合 1：跨仓库 + 可编程 —— 组织级 issue 盘点（P6/P7） $ gh search issues --org my-org --label bug --state open \ --json repository,title,url --jq '.[] | "\(.repository.nameWithOwner) \(.title)"' # 组合 2：可编程 + 万能接口 —— 查出再改（P6，两步走） $ ITEM_ID=$(gh project item-list 1 --owner my-org --format json --jq '.items[0].id') $ gh api graphql -f query="mutation { … itemId: \"$ITEM_ID\" … }"
注意：通用范式是"--jq 结果塞进变量，再喂给 gh api"——从"用 gh"到"用 gh 做自动化"的分水岭；批量前先单对象验证。
退出

破局完成：带着结果回到原 Purpose

支撑层的完成态就是被打断的 Purpose 得以继续。每次返回时问一句："这个问题下次还会遇到吗？"——会，就固化成脚本/别名（定义归 P1），这是支撑层唯一会"沉淀"下来的东西。
